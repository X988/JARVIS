ЦЕЛЬ

Нужно развернуть на сервере компании self-hosted систему AI-агента под рабочим названием JARVIS.

JARVIS должен принимать от администратора голосовые и текстовые команды с телефона, понимать задачу, анализировать инфраструктуру и безопасно выполнять разрешённые административные и программные действия.

Система предназначена для реальной корпоративной инфраструктуры, а не для демонстрации.

Главные сценарии:

- системное администрирование Windows Server;
- Linux-администрирование;
- диагностика серверов;
- работа с Active Directory;
- работа с DNS/DHCP;
- администрирование SQL Server;
- резервное копирование баз 1С;
- проверка резервных копий;
- работа с файловыми серверами и NAS;
- Docker;
- Mailcow;
- MikroTik;
- WireGuard;
- мониторинг;
- запуск PowerShell;
- запуск Ansible;
- запуск заранее подготовленных административных процедур;
- Git и GitHub;
- анализ кода;

ГЛАВНЫЙ ПРИНЦИП АРХИТЕКТУРЫ

Нельзя давать LLM неограниченный root, Domain Admin или SQL sysadmin и разрешать ей произвольно выполнять любые команды.

→ Target Infrastructure.

ПРИМЕР

Пользователь отправляет голос:

«Джарвис, сделай резервную копию базы utp».

JARVIS должен определить примерно:

intent = database_backup
system = 1C
database = utp
target = определённый SQL Server
destination = определённое backup-хранилище

Перед выполнением проверить:

- сервер доступен;
- SQL Server доступен;
- БД существует;
- БД ONLINE;
- backup destination доступен;
- хватает свободного места;
- нет ли уже выполняющегося backup;
- разрешено ли пользователю это действие.

После этого выполнить соответствующий automation template.

Не генерировать каждый раз новый произвольный PowerShell-код, если уже существует утверждённая процедура backup.

---

BACKUP 1C / SQL SERVER

Реализуй отдельный модуль для резервного копирования SQL Server баз, используемых 1С.

Он должен поддерживать:

- список разрешённых SQL Server;
- список баз;
- mapping база → сервер;
- backup destination;
- retention policy;
- compression;
- checksum;
- timestamp;
- журналирование;
- проверку результата.

Пример файла:

utp_YYYY-MM-DD_HH-mm-ss.bak

После backup:

1. проверить наличие файла;
2. проверить размер;
3. выполнить SQL-проверку backup;
4. записать результат;
5. уведомить пользователя.

Отдельно предусмотреть периодическое тестовое восстановление backup во временную БД.

Не считать простое существование .bak доказательством работоспособности резервной копии.

УРОВНИ РИСКА

Каждое действие должно иметь risk_level.

LEVEL 0 — READ ONLY

Примеры:

- посмотреть logs;
- CPU;
- RAM;
- routes;
- disk;
- status;
- git diff;
- CI status.

Выполнять без дополнительного подтверждения.

LEVEL 1 — LOW RISK

Примеры:

- создать backup;
- диагностические команды;
- запустить безопасный approved job.

Можно выполнять автоматически.

LEVEL 2 — CHANGE

Примеры:

- restart service;
- deploy;
- update package;
- создать пользователя AD;
- изменить конфигурационный файл.

Требуется confirmation.

LEVEL 3 — CRITICAL

Примеры:

- reboot server;
- reboot Domain Controller;
- firewall changes;
- MikroTik route/firewall changes;
- database restore;
- database deletion;
- mass AD modification;
- destructive filesystem operations.

Требуется явное подтверждение.

Для особо опасных операций — двухэтапное подтверждение.

ПОДТВЕРЖДЕНИЕ

Не принимать обычное слово «да» без контекста, если между запросом и подтверждением прошло много времени.

Создавай approval_id.

Например:

APPROVAL-20261006-0017

Пользователь получает:

Планируется:

Restart DC01

Последствия:

- Domain Controller
- DNS
- DHCP

Активных пользователей: 14

Подтвердите:
CONFIRM APPROVAL-20261006-0017

Approval должен иметь TTL.

Например 5 минут.

---

ПРАВИЛА РАБОТЫ АГЕНТА

Не ограничивайся рекомендациями.

Если у тебя есть доступ к серверу и репозиторию:

- создавай файлы;
- устанавливай зависимости;
- исправляй конфигурацию;
- пиши код;
- запускай тесты;
- проверяй результат.

Но не выполняй необратимые или высокорисковые действия без explicit approval.

Если находишь ошибку — исправляй.

Если компонент отсутствует — реализуй.

Если архитектура небезопасна — переработай.

Если можно решить проще — используй более простое решение.

Не добавляй технологии только ради сложности.

---

КРИТЕРИИ ГОТОВНОСТИ

Первая версия считается рабочей только если выполняются все условия:

1. JARVIS принимает текст из Telegram.
2. Принимает voice.
3. Whisper корректно преобразует voice в текст.
4. Пользователь проходит allowlist.
5. intent распознаётся.
6. policy engine проверяет действие.
7. read-only команды выполняются.
8. backup базы работает.
9. результат backup проверяется.
10. critical command требует approval.
11. все действия попадают в audit.
12. secrets отсутствуют в коде.
13. после перезагрузки сервера система автоматически запускается.
14. есть backup самой системы.
15. есть инструкция восстановления.
16. есть DRY_RUN.
17. базовые integration tests проходят.

ФОРМАТ РАБОТЫ

Сначала изучи текущее состояние сервера.

После этого выдай краткий план:

1. что уже установлено;
2. что будет использоваться;
3. какие компоненты нужно добавить;
4. какие риски обнаружены.

Затем приступай к реализации.

Не останавливайся после создания архитектурного документа.

Продолжай до реально работающего MVP.

После каждого крупного этапа проверяй результат реальными командами.

В финале предоставь:

- архитектуру;
- список контейнеров;
- список сервисов;
- список портов;
- список созданных файлов;
- список учётных записей;
- список permissions;
- список runbooks;
- список доступных голосовых команд;
- инструкцию запуска;
- инструкцию backup;
- инструкцию restore;
- результаты тестов;
- известные ограничения;
- перечень функций следующей очереди.

Главная цель:

создать не демонстрационного чат-бота, а безопасного корпоративного AI-агента системного администратора, которым можно управлять голосом с телефона и который способен выполнять реальные задачи на Windows, Linux, SQL Server, 1С, MikroTik, Docker и GitHub-инфраструктуре.
